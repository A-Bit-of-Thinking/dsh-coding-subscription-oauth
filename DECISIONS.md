# Decisions

## RCB-2026-10-08 — Local Claude callback bridge

- **Tier / owner:** F1 / implementation task owner.
- **Goal:** A configured browser computer can complete remote Claude authorization without copying the callback. Remote DSH's persisted provider status is the acceptance result.
- **Facts:** The pinned OAuth implementation starts a loopback listener at port 53692 before publishing a challenge and accepts a complete callback URL through the existing authenticated code-submission route. State, PKCE, credential exchange and persistence remain native. A remote browser's localhost points to the browser computer. SSH requires additional cloud access that browser sign-in does not otherwise need.
- **Choice:** An opt-in local daemon receives a challenge through top-level browser navigation and pins the configured DSH origin. By default it prepares its local receiver, opens Claude, then returns a matching callback to the exact DSH origin in a URL fragment. The DSH client erases that fragment immediately, matches the fresh pending challenge, and submits through its existing authenticated route. It reports success only after persisted signed-in status carries a completion receipt for that same login attempt. An existing account surviving a failed or canceled exchange is insufficient. Explicit SSH/IAP forwarding remains an optional transport. Credentials stay with remote DSH.
- **Guardrails:** No background clipboard access, cross-origin local-network fetch, arbitrary shell arguments from webpages, host-key bypass, public callback listener, or new remote credential endpoint. Automatic submission includes its login-operation ID, checked before consuming the native prompt, so a stale return cannot disrupt a newer login. Older cancellation and model/active-account/removal refreshes cannot replace a live pending login. Preparation expires after 30 seconds; a pending callback expires after five minutes. Installed macOS startup is per user and removable; canceling startup stops further discovery and never reports readiness.
- **Assumptions / unknowns:** The browser has an existing DSH session and runs a package containing the return consumer; the local helper is installed on that computer. SSH/IAP access is required only for explicit native-forwarding mode. Real provider acceptance and a deployed host remain separate verification layers.
- **Rollback:** Select callback paste in Settings and uninstall the owned local LaunchAgent. The native OAuth flow remains available.
- **Reopen condition / review:** Review on the first real host verification, or when the provider supports an approved remote redirect and a local helper can be removed.
- **2026-10-08 review amendment:** An injected installer regression showed that a registered service without an owned file could be claimed and later stopped by uninstall. Installation now refuses before writing or starting it. Native auth fixtures completed at 30.5 seconds or after a lost acknowledgement/status response while the previous return page permanently reported failure. Observation now lasts up to 60 seconds, recovers the same attempt's receipt without resubmitting its callback, and reports an unconfirmed result on exhaustion, requiring an account-status check before retry. Keyboard regressions showed the new overlay left focus on background controls; the return dialog contains focus and restores prior focus and inert state on disposal. These are candidate-level checks, independent of real provider or deployed-host acceptance (`DAO-REALITY`, `DAO-TRUST`).
- **2026-10-08 native lifecycle amendment:** An isolated native credential-store regression showed that a delayed logout could delete a subsequently completed login's credential. New sign-in now returns a retryable conflict until the coalesced sign-out operation finishes, including a second guard after method-switch cancellation. Another regression completed a partially read login request after route disposal and restarted authorization on the disposed instance. Disposal closes admission synchronously; accepted requests that resume afterward receive a conflict instead of starting a latent operation. These changes protect the existing native state and credential store without queuing login requests (`DAO-REALITY`, `DAO-FOCUS`).
- **2026-10-08 cancellation and recovery amendment:** Native file-store regressions showed that retries during a draining cancellation reused an aborted challenge, and disposal could return before an older logout deleted a replacement owner's credentials. Admission now rejects active aborted operations, disposal awaits its owned logout, and stale logout requests cannot start on a disposed instance. Real HTTP return fixtures also showed permanent false failure after a transient first status read, a proxy 502/503 acknowledgement following acceptance, or manual code delivery winning an in-flight automatic request. Recovery revalidates the pending challenge before one automatic submission and observes only that attempt's receipt after ambiguous acknowledgement, within the existing deadline. Permission rejection, cancellation, replacement and exchange failure remain separate terminal conditions (`DAO-REALITY`, `DAO-TRUST`).
- **2026-10-08 readiness classification amendment:** Registered HTTP auth-route fixtures completed manual delivery before the automatic return's first successful status read, either before mounting or during transient initial-read recovery. The native owner reported signed-in with the completed attempt's receipt while the page falsely claimed failure. Without a captured pending challenge, the page cannot correlate that receipt to its callback. It now reports an unconfirmed result and directs the user to account status, with no automatic submission or success inference. A stored operation error remains a failure (`DAO-REALITY`, `DAO-FOCUS`).
